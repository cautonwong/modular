# ADR conformance

Tracks how far the current implementation matches the decisions in
[`adr.md`](adr.md) (D1-D85). `adr.md` is the single decision source and this file
is the **only** decision-vs-implementation view; `todo.md` (D1-D45) is an archived
early subset.

Legend: ✅ implemented · 🟡 partial · ❌ not implemented · ⛔ contradicts the ADR · 🚫 wontfix (decided not to do).

## Runtime, events and faults

| ADR | Decision | Status | Evidence |
|---|---|---|---|
| D47 | Single runner context; `sys_step()` decomposable | ✅ | `edge_sys_step()` + `edge_sys_run()`; on an RTOS the runner parks on a notification and is woken from the ISR instead of polling, with the yield policy, the module-vs-task suspend boundary and the priority mapping written down in `docs/rtos-runner.md` |
| D51 | `poll`/`on_event` (+ optional `suspend`/`resume`); `init`/`deinit` outside the struct | ✅ | `edge_module_t` carries `poll`/`on_event`/`power_off`/`suspend`/`resume` only; the composition root calls `<app>_init(self)` / `<app>_deinit(self)` (products do, reverse order at shutdown). Enforced by `check_module_contract.py`. `power_off` stays in the struct because *ordering* is a `sys` duty (D11) |
| D52 | Event-driven + periodic mixed scheduling; idle -> board | ✅ | `period`/`budget`/`edge_sys_idle` hook; the product idle hook feeds the watchdog and calls the board low-power action, then the atomic PAL wait. On the RTOS the idle hook is reached while the runner is parked, and the scheduler's tickless sleep sits below it |
| D53 | Non-fatal init failure skipped and recorded | ✅ | `fatal` flag: default skip, `fatal` rolls back |
| D54 | Drop-newest + counter; multi-subscriber; unsubscribe | 🟡 | All done, except multi-SPSC producer queues |
| D55 | Central `edge/modules.h`, `0xNN00` segment, allocated in blocks per owning layer | ✅ | Table-driven `EDGE_MODULE_IDS` (one line per ID; assertions generated from it); `check_module_ids.py` rejects duplicates, misaligned values, out-of-block values and layer tokens without a block |
| D56 | ABI version object | 🟡 | `_Static_assert` layout only |
| D65 | One SPSC queue per producer | ❌ | Single caller-owned queue + injected `edge_irq_guard_t` |
| D66 | Scalar event + token; payload read through a port | ✅ | The rule is written where implementers look (`edge/event.h` next to `edge_event_t`, plus `docs/payload-token.md`): the payload stays in the producer's buffer, the consumer reads it through a port it defines (D14; `edge_byte_reader_t` is the canonical byte shape), and a frame is invalidated by the next event with the same id. `tests/test_payload_token.c` pins both halves, including the *checkable* form: when the token is a generation the consumer's port can refuse a stale one, so the lifecycle rule stops being a discipline. Not enforced by a gate, and cannot be: `check_event_payload.py` sees scalar fields and cannot tell a length from an address, which is why the anti-pattern is documented rather than detected |
| D67 | API catalogue (framework/runtime/platform/ports) | 🟡 | `errors.h`/`modules.h`/`ports.h` present; naming is `edge_sys_*`, not `sys_*` |
| D69 | Bounded runner step | ✅ | `max_events_per_run` (default 8), one due poll per module per step |
| D70 | Reentrant `sys_publish` deferred into a runner queue | ✅ | `edge_sys_publish()` + `pending_high_water` |
| D71 | Atomic idle/low-power sequence in board/PAL | ✅ | `edge_os_idle_wait(pal, pending, ctx)` = critical-enter -> re-check (`edge_sys_pending`) -> `pal->idle` (Cortex-M `WFI`) -> critical-exit; board provides enter-low-power / feed-watchdog / reset; `edge_sys_healthy` is the watchdog input. The boundary is explicit: `pal->idle` is the raw wait primitive and must not contain the sequence (it would double-mask and re-check outside its own protection). ISR half: `edge_rtos_irq_guard()` brackets the push in a BASEPRI save/restore |
| D72 | Wrap-safe tick comparison | ✅ | Deadlines use the modular compare `(int64_t)(now - due) >= 0` in `sys/runtime/src/sys.c`; extending a *counter* across a wrap is a different operation and is stated the other way in `pal/os/include/pal_os/tick64.h` (unsigned `now < last` carry, with the once-per-2^31-tick sampling ceiling), host-tested in `tests/test_tick64.c`. The two are documented together so they cannot be mixed up |
| D74 | `sys_stats` aggregate | ✅ | `edge_sys_stats_t` + `edge_sys_stats_reset()` |

## BLDC / VESC port (phases A-E, in progress)

The `bldc` family ports `vendor/bldc` (VESC) into this architecture. Plan, the six
completion criteria and the phase route: [`bldc-migration.md`](bldc-migration.md).
This table is the drift view required by that plan, not a second plan. A decision
number for the family is deliberately left to the maintainer.

Porting rule applied throughout: the reference source is the only authority, and a
claim of "1:1" is only made where a differential harness compiles the reference and
compares it (14/14 in the util harness, 8/8 in the motor harness at the time of
writing).

| Area | Status | Evidence / divergence |
|---|---|---|
| FOC math (Clarke/Park/SVPWM, sincos, atan2) | ✅ | Differential: `foc_svm` matches over 6561 vectors (max duty difference 1.5 integer counts, the reference's own rounding). The earlier `v/(v_bus*sqrt(3)/2)` normalisation was a sqrt(3) error, fixed in `cf5baaf` |
| Observer family (7 types) | 🟡 | Differential: bit-identical to `foc_observer_update` for all seven (max abs phase and state delta 0.000000 over 4000 steps each). Parameter compensation is ported as well and verified with it ENABLED: `foc_observer_adjust_params` reproduces the reference's saturation, temperature and saliency block bit-exactly for FOC_SAT_COMP_FACTOR and FOC_SAT_COMP_LAMBDA_AND_FACTOR, with and without temperature compensation. Still open: nothing in this row - `foc_core` carries the two configuration fields and the product supplies the motor temperature (B4) |
| PLL | ✅ | Differential: bit-identical to `foc_pll_run`; the non-reference phase differencing it replaced is deleted |
| Decoded app inputs, statistics, energy counters, tachometer | ✅ | Wire bytes pinned per command; reset/read-reset semantics covered by tests |
| Average sampler tick | 🟡 | The reference samples on a dedicated periodic thread and keeps summing while the motor is idle (reusing the last vd/vq); this port accumulates in `foc_core`'s periodic `poll` and adds nothing to vd/vq while idle |
| Energy counter tick | 🟡 | Reference accumulates in the MC timer ISR with that timer's dt (`mc_interface.c:2036`); this port accumulates in the FOC loop with the loop dt. Same integral, finer sampling |
| Statistics inputs | 🟡 | Power statistic uses the unfiltered bus voltage; `count_time` returns 0 (needs a clock this module is not given); the motor-temperature statistics report the filtered NTC reading the product's sampler hands in (B4) |
| Fields with no source | 🟡 | Three MOSFET temperatures and the timeout/kill-switch status return 0; the motor NTC now has one (the product's sampler, B4), which is also how the reference's own `m_temp_motor` is produced. Both temperature seeds start at the reference's 0: this port used to start the FET one at 25 degC, and that choice is gone. Input current is the reference's power-balance estimate, not a DC measurement. Same policy in COMM_GET_VALUES_SETUP: odometer_m (needs a persisted counter, and the reference's own per-motor accumulation site has not been located, so a number would be invented) and uptime_ms (this module is given no clock) return 0; num_vescs stays 1 because the reference aggregates unexpired CAN status frames and this product has no CAN status receive path; controller_id is 1 until the app configuration reaches that adapter. Its battery level uses the bus voltage where the reference filters a slower input voltage |
| Speed and position control loops | 🟡 | The speed loop is now the reference's `foc_run_pid_speed` fed by `s_pid_*`, bit-identical over four configurations (`26e805c`). Still open: the position loop, which the reference drives with `p_pid_*` while this port uses a fixed `err_pos * 0.1f`. Open-loop drive is ported - `foc_core_set_openloop_current` (mcpwm_foc.c:878) and the loop branch it selects (:3607-3609) - and that was B5's real blocker: both flux-linkage procedures spin the motor up through it before they measure anything. One nuance is not modelled and is named in the code: the reference keeps its running state separate from its control mode, so a current below `cc_min_current` selects the mode without starting; here the mode is the state, so that case writes the setpoint and stays where it was. The release and modulation-off interaction (`m_motor_released`, `m_current_off_delay`) stays with the B3 note above |
| Current-command path | 🟡 | DIR_MULT (`m_invert_direction`) is now applied where the reference applies it - current, brake, duty, pid_speed - and the port's invented clamp to `[current_min_a, current_max_a]` is gone, since `mc_interface_set_current` never limits (`mc_interface.c`). `COMM_SET_CURRENT_REL` follows `mc_interface_set_current_rel`: the limit base is chosen from the duty's sign, which is why it lives in the motor side (the codec has no duty). One divergence inside that: the reference chooses between the *effective* limits `lo_current_max` / `lo_current_min`, which `update_override_limits()` derives at runtime as the smallest of the current, rpm, acceleration, temperature, duty and input-current limits, whereas this port uses the stored `l_current_min`. They agree only while no other limit binds, so the effective-limit computation is still to do. `lo_current_max/min` are runtime values and are deliberately not serialised here (the reference does not serialise them either). Closed since: the reference's `m_current_off_delay` and the modulation-off gate that reads it (`mcpwm_foc.c:3952-3975`). `foc_core_release_motor` sets the flag and zeroes both setpoints; the control loop then stops the modulation once the delay has run out and every setpoint is below the minimum - which is also the release path B5's flux-linkage procedure ends with, and it closes the divergence this row used to carry. The one piece not wired is the arming setter: `mcpwm_foc_set_current_off_delay` (:1114, a maximum rather than an assignment) is reached by COMM_SET_CURRENT_OFF_DELAY, which this port does not handle. Still open: brake, which needs its control mode: the reference's brake is not a negative current but `CONTROL_MODE_CURRENT_BRAKE`, whose meaning is spread over the loop - the braking current opposes the speed (`mcpwm_foc.c:3450`), its magnitude is capped at the magnitude of lo_current_min (`:3328`), the duty-based limit base switches to the positive limit (`:3391`), min-rpm hysteresis is cleared (`:4091`), and a 10-cycle state machine keeps all phases shorted until the braking current reaches its target (`:3350`) - with field weakening involved (`foc_math.c:722`), so it shares state with B3. The port keeps its approximate negative current rather than flipping the sign without that mode. Handbrake is done: `FOC_STATE_HANDBRAKE`, the setpoint on the q axis, no abs and no DIR_MULT, the electrical phase forced to zero (`mcpwm_foc.c:3602`) so it locks the rotor instead of driving it, and `COMM_SET_HANDBRAKE` on the wire at 1e3 |
| Reported duty | ✅ | `COMM_GET_VALUES`' duty field now carries `SIGN(vq) * NORM2_f(mod_d, mod_q) * p_duty_norm` (`mcpwm_foc.c:3818`) instead of the phase-A duty, which is a different quantity. `p_duty_norm` is `TWO_BY_SQRT3` because `foc_overmod_factor` defaults to 1.0 and is not a configuration field here yet |
| HFI (sensorless start) | 🟡 | The angle tracker is ported and bit-exact: `foc_hfi_adjust_angle` (foc_math.c:766-778) - the `foc_hfi_max_err` truncation, the proportional term with the reference's double-literal gains (4000.0 / 10.0, which the reference's own TODO admits are unreviewed, so they are copied rather than tidied), the double integrator bounded by the fast speed estimate, and the wrap. Its differential harness links the reference's motor/foc_math.c unmodified, and the 36 golden vectors in test_foc_core are that run's own output. Still open: everything that actually excites the motor - the six-vector and V0V7 injection, the per-PWM-cycle current sampling, the flip counters, the `foc_hfi_amb_mode` gating and the handover to and from the observer. Not to be ported, decided here rather than discovered during the port: the reference's plotting hooks (`commands_send_plot_points`, `m_hfi_plot_en`, `m_hfi_plot_sample`, and the two branches that feed the upper computer's plot tab) are a host-side diagnostic with no consumer in this repository, and what they would add - a sample stream and a debug view - is what the tests and the golden vectors already are. The rest of the machinery has its own map: the state struct `hfi_state_t` (foc_math.h:60-95), the sample-table selection `update_hfi_samples` (:133-166, whose three cases pick 8/16/32 samples with table_fact 4/2/1 and the matching FFT pair), the core at `hfi_update` (:4218, with the speed gate at :4222, the six-vector path, the D_DOUBLE_PULSE path and its buffer-slot conventions), and the handovers at :3558-3591 and :3748-3779. The reference drives it from a thread of its own (:69-71, :576), which this port will instead step from the fast loop. Fixed on the way there, and worth naming because it affected more than HFI: this port defined `M_PI` as a float literal where the reference uses glibc's double, so every angle wrap in both trackers landed about one float ULP away and accumulated over thousands of steps |
| Motor detection | 🟡 | The resistance measurement is ported from `mcpwm_foc_measure_resistance` (mcpwm_foc.c:1797-1908): the forced electrical phase (the reference's `m_phase_override`, which stops both the sensor and the observer branches being taken), CURRENT mode with id = 0, the abs(I)/200-per-millisecond ramp, the 50 ms lock wait, the accumulator the control loop fills (now in foc_core, gated on the control having run, read and cleared through separate calls because the reference uses them at different moments), the two averages divided in that order, both fault aborts, and the cleanup the `stop_after` flag gates. Its timing is the reference's: one millisecond of the procedure per accumulated millisecond, and the millisecond that reaches the target is the ramp's last. The inductance measurement is not ported, and cannot be until B2 is: `mcpwm_foc_measure_inductance` switches the configuration into FOC_SENSOR_MODE_HFI and drives the HFI voltages (:1927-1935), so it and COMM_DETECT_MOTOR_R_L that contains it wait on HFI. The flux-linkage and hall procedures are not read yet. All three answer EDGE_ENOTSUP rather than a plausible number, and the invented crawl and timing arithmetic this module used to carry for them is gone. Still open: everything except resistance, plus the COMM_DETECT_* wiring that drives it. The open-loop flux-linkage procedure is ported now, and it is not in `mcpwm_foc.c` at all: both variants live in `conf_general.c`, and the open-loop one (`conf_general_measure_flux_linkage_openloop`, :967-1316) is a blocking mill that this port turned into a state machine with the resistance one as its template - the 200-step standstill ramp (whose reference has no sleep in it, so it runs inside one millisecond here too), the thousand-millisecond baseline of what the motor draws without turning, the spin-up with its three failed exits (-1 the fifteen-second timeout, -2 the duty falling under seven tenths of the highest it reached, -3 a target that never rose above 1.1 times the standstill draw), the ten-thousand-millisecond average, the linkage formula `(v_mag - res * i_mag) / rad_s - i_mag * ind` with the ramp's own speed rather than a measurement, and the two-thousand-millisecond back-EMF average taken only where the duty is below a fiftieth. It carries the reference's own -1, -2 and -3 rather than folding them into a status, and puts the temporary configuration back on every exit path. Two things it does not carry, named in the code: the observer gain it writes after a success (not a configuration field here) and the encoder-ratio half of the back-EMF phase (sensored, and this board has no angle source). Still open: the hall procedure (no hall port), `mcpwm_foc_measure_inductance_current` (:2086) and `res_ind` (:2320), which route through `mcpwm_foc_measure_inductance` and so wait on B2, and the COMM_DETECT_* wiring that would drive any of them. The sensored variant is ported too now (`conf_general_measure_flux_linkage`, :742-899): the same state-machine treatment in `motor_id.c`, with its four attempts to spin the motor up - each of the last three releasing it and loosening a start-up limit, the values being the reference's own (cycle integral limit 250, then the minimum speed doubled with the limit at 20, then the speed quadrupled with the commutation mode delayed) - and its two thousand milliseconds of averaging, where the measured current's own drop over the winding comes off the voltage before the linkage is that over sqrt(3) times the angular speed. Its result carries a linkage but its success is the state, because the reference returns a bool; and unlike the open-loop one its encoder fields are real. It is wired now: the product's glue answers the port's new callbacks, and COMM_DETECT_MOTOR_FLUX_LINKAGE drives it with the reference's own request and a reply that is a single linkage, because that is all the reference's handler sends. One thing the glue cannot carry is named rather than discovered during the wiring, and it is the only piece of this procedure that does not survive the port: the per-attempt start-up limits (sl_min_erpm, sl_cycle_int_limit and the delayed commutation mode) are fields this port's FOC configuration does not have, because they tune the reference's sensorless start and this controller does not use them. The setter is a documented no-op, which makes the four attempts differ only by the release and the re-drive - the attempt that matters is the first one plus its retries, not the tuning between them. The hall detection procedure is registered as a deliberate non-port with a trigger rather than left as an omission: it needs raw hall inputs - its reply is an eight-byte hall table and a bool - and no product in this repository has any, so the port would have no consumer. It arrives with the first board that has halls, or with a host simulation that grows them |
| Saturation and temperature compensation | 🟡 | Saturation compensation (all three `foc_sat_comp_mode` branches) and the saliency term are ported and verified bit-exactly against the reference's block for FOC_SAT_COMP_FACTOR and FOC_SAT_COMP_LAMBDA_AND_FACTOR. Temperature compensation is now carried end to end: `timer_update`'s cycle-time recomputation (mcpwm_foc.c:3939-3948) with its `-30` degC floor and the `0.00386` coefficient, consumed by the observer's resistance and by the current loop's `ki`, both gated on `foc_temp_comp`. ## Open conflicts

1. **D65 (multi-SPSC)**: the implementation deliberately uses one queue plus an
   injected IRQ guard, which is the scheme the ADR chose *against*.
2. **API naming**: the ADR catalogue uses `sys_run/sys_step/sys_idle/...`; the
   implementation uses the `edge_sys_*` prefix.
## Recorded deviations

**The BLDC detection pair.** `COMM_DETECT_MOTOR_PARAM` and `COMM_DETECT_APPLY_ALL_FOC` are refused
by name in the codec rather than by its default, because what stops them is not that nobody wrote
them yet. The parameter detection drives the motor with the BLDC six-step commutator - it stages
`MOTOR_TYPE_BLDC` with a sensorless start, an integrating commutation mode and its own `sl_*` limits
(conf_general.c:514-536) - and builds its hall table and BEMF coupling constant from that drive and
the raw hall inputs; this port has no six-step commutation layer and no product with halls, the same
disposition the hall procedure itself carries. The all-in-one detection is that procedure plus the
others behind a DC-offset calibration (conf_general.c:1747, `mcpwm_foc_dc_cal`), and this port's
phase currents come from a mid-scale offset with no calibration pass. D14, B5

**HFI's step sign.** The reference's six-vector excitation records an
inverse-inductance entry only when the current's step across the two sampling
instants of one injection cycle is positive (`mcpwm_foc.c:4957`), and on this
checkout that gate never fires: its own branch order stores the previous sample
before driving the negative injection half and samples in the positive one, so
the step it measures is always the response to the negative half - measured in
the host closed loop at -2.2 A, which is past the 0.01 threshold in magnitude and
on the wrong side of it, leaving all thirty-two entries at zero and the tracker's
angle driven by nothing. What the gate selects for is the magnitude of the step,
and what it writes is the inverse inductance, which its own comment calls
positive, so the port takes the negative-going step and negates it: same
structure, same branch order, same threshold, same quantity in the buffer. With
that, the buffer fills (about 11000 to 12800 1/H across the table angle) and the
tracker follows a rotor parked at 0.7 rad to within 0.004 rad. The half-turn the
second harmonic cannot tell apart stays on the right side because the speed gate
and the observer's zero-time window keep the held angle on the observer's;
resolving it from the first harmonic needs machine saturation, which the linear
virtual motor does not have and the path's unit test covers instead. D14, B2
